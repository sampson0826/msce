This is the diagnostic distinction:

The DAO: c(p) ≈ 0, Σ||∇σ|| ≫ 0 → Type III dark zone (cancellation)

Both produce ||Π|| ≈ 0. Both are undetectable by traditional audit. But they have different root causes and require different fixes.

Dark Zone Taxonomy — Two Species, One Framework

Type III Dark Zone

Example: The DAO (2016)

Mechanism: Multiple constraints have strong individual gradients that point in opposite directions → Σ∇σ ≈ 0

Signature: c(p) → 0, Σ||∇σ|| ≫ 0

Detection: DarkZoneDetector (cancellation_eps)

Fix: Break the gradient alignment. Move one constraint's activation region so the cancellation can't occur.

Danger level: Highest. Invisible because each constraint appears to be "working" — strong but canceling.

Cold Start Gap

Example: Parity Wallet (2017)

Mechanism: The initial state sits in a region where no constraint has activated yet.

Signature: c(p) → 1, Σ||∇σ|| ≈ 0, ||Π|| ≈ 0

Detection: ResidualDetector (||Π|| < ε)

Fix: Add a deployment constraint that ensures the system starts in an activated region.

Danger level: High. Visible if you check the initial state, but traditional audits check code correctness, not initial-state topology.

How a Dark Zone Scanner Would Have Caught Parity

Step 1: Constraint Modeling

Auditor defines 2 rules:

• init_guard: only_uninitialized prevents re-init

• owner_guard: only_owner prevents unauthorized kill

Scanner asks: "At state (x=0, y=0), what is ||Π||?"

Step 2: Residual Scan

||Π(0,0)|| = 0.2709 < ε=0.15

→ RESIDUAL DETECTED at the origin

But c(p) = 0.9999 → NOT a cancellation

Classified as: cold start gap

Step 3: Remediation

Scanner recommends:

• Add deploy_order constraint (L1 lifecycle)

• Ensure library contract is initialized at deploy time

• OR: make the library contract non-initializable directly (pure library, not a standalone contract)

Fix verified: ||Π|| at (0,0) rises from 0.2709 to above threshold

The Missing Third Constraint

deploy_order constraint (currently certainty=0.1):
In the Parity system, the library contract SHOULD have been either:
1. Initialized at deployment (constructor-sets-owner), or
2. A "pure library" that cannot be called directly (only via delegatecall)

Without this, the system has a structural cold start gap: the initial state (x=0, y=0) has zero protection from BOTH init_guard and owner_guard.

With deploy_order activated (simulated): the initial state would be pushed to (x≥0.3, y≥0.3) before any user interaction, closing the gap.
This is the constraint engineering equivalent of "initialize before use" — a rule so basic it's invisible until it's missing.
